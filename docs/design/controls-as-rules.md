# Accepted controls as the organization's rules

Design note. Builds on control records and types (`sms-controls.ts`, `control-types.ts`, migration 0056), the generic evaluator and adoptions with modes (`rule-evaluations.ts`, `adoptions.ts`), and release policy version 2 (`mission-release-findings.ts`).

## 1. The declaration on a control type

A control type gains an optional `rules(parameters)` beside `describe`, `validate` and `area`. It turns valid parameters into zero or more rule declarations, each: the target subject kind, optionally the listed subject ids that alone are in scope, the reads, a check kind (id and version) with its parameters, and optionally applicability and wording. Core code builds the leaf from it with `defineCheckedRule`; it names no control type and no check kind.

- Like `describe`, the declaration is not part of the type's digest, so adding it changes no accepted control. What it produced is pinned instead: by the leaf digest, inside the pack digest, inside the adoption.
- **Operating limit** declares the mapping its author wrote down: `value.within-limit` version 1 on the stated field of the latest observation of the stated type and version about the target. The target is the kind of subject the control names; a limit for the whole organization gives one rule per kind of subject the observation type reports on, since a rule has one target kind. For listed subjects the rule applies only where the latest observation's subject is listed (applicability on `subject.id`, reading observations whose subject is of that kind), and only those subjects are in scope.
- **Avoidance area** declares no rule. Route review keeps its geometry check unchanged and reads accepted area controls as today.
- A type that is not checked automatically (the described measure) declares nothing and is shown as needing a person's confirmation.

## 2. Which controls are in force

A control version is in force when its hazard's latest risk acceptance binds it, the hazard is not closed, the control record is not withdrawn (closed), and the instant lies in its effective interval [effectiveFrom, effectiveUntil). A control revised after acceptance keeps its accepted version in force until a new acceptance binds the new version or the control is withdrawn: what a person signed stays the rule until a person signs again.

## 3. The organization pack

- **Identity.** Pack id `ledger.accepted-controls`, one pack per organization: adoption rows, evaluations and findings are already per tenant, and finding ids include the tenant. The registry refuses this id, so no shipped pack can claim it.
- **Leaves.** One per accepted control version and target kind, ordered by id: id `ledger.accepted-control.<control record id>.<subject kind>` (stable across control versions, so a finding follows its control), version = the control's version number, title = the control's title. Source kind `operator_procedure`; its text is the control's own wording (its type's `describe`), its reference names the control record, version and body digest.
- **Versions.** Each SMS decision that can change the set (`risk.accept`, `record.close`, `record.reopen`, on a hazard or a control) assembles the set in its own transaction, after locking the organization row. So does each instant at which a bound control's effective interval starts or ends (section 4a). When the leaves differ from the latest version's, version N+1 is recorded; otherwise nothing is. Two concurrent decisions serialize on the organization lock, so versions are linear.
- **Adoption by acceptance.** Version N+1 is adopted in active mode as an ordinary `rule-pack.adopt` journal event and `organization_pack_adoptions` row: interval from now with no practical end (9999-12-31), revising the adoption of version N. Its actor is the person whose decision caused it, with authority policy `ledger.accepted-control-rules.1`, the capabilities that decision checked and the decision's id. No `pack:adopt` is asked of them: the signed acceptance, or the withdrawal by someone allowed to withdraw, is the act.
- **History.** Nothing is rewritten. Earlier adoption rows stay and show as revised; earlier evaluations keep the pack version, leaf version and digest they ran under. A removed rule's open findings stay open until a person resolves them, as for any rule.
- **Labels.** The pack says what it is: `status: assembled` (Ledger assembled it) and `review: accepted_and_signed` (every rule quotes a control version a person accepted with a signature). These are values the pack schema allows only for this pack: the registry refuses a pack that carries them, and no shipped pack does, so no shipped pack's digest moves. Versions recorded before the labels existed carry `draft` and `ai_drafted` and stay valid as recorded; their digests recompute from what they hold. Since a version is recorded only when its leaves change, the labels appear from the next change on. `adopted` stays `false`, as for every pack: the adoption is what makes it adopted. The leaves keep the leaf schema's `ai_drafted` label.

## 4. Several API and worker processes

Nothing is registered in memory, at startup or after an acceptance. The evaluator already reads every pack from the adoption record in the database (`adoptionsInEffect`), never from the registry, so every process sees version N+1 once the deciding transaction commits. The ordinary worker projects the adoption (`projectPackAdoption`) and, because it revises N, queues again every subject an earlier version of each rule evaluated (`queueRuleEvaluationsForAdoptionRevision`): a changed limit is evaluated again without new data. A new rule is evaluated on the next observation it reads. Shipped packs' registration and digests are unchanged.

## 4a. Effective intervals

A control's rule is in force exactly while the control's effective interval is.

- **Scheduling.** When the worker projects an SMS decision that can change the set, it queues a `control-boundary` row in the generic evaluator's queue (`rule_evaluation_work`) for every later instant at which a bound control's interval starts or ends. The row's subject is the organization, its due time the instant, its trigger event the decision. A unique index (migration 0069) keeps one row per organization and instant, so decisions that name the same instant, or two workers projecting at once, queue it once. Nothing waits in a process: the row is leased like a deadline once it is due, by whichever worker runs, and a worker that loses its lease commits nothing.
- **Reassembly.** The worker that leases the row assembles the set in force now, as a decision does: under the organization lock, adopting version N+1 from now only when the leaves differ. Its adoption names the worker as actor with policy `ledger.accepted-control-interval.1`, the instant (`boundaryAt`) and the decision that scheduled it (`scheduledBy`); no capability is checked, since the interval was part of what a person signed. A row whose instant changes nothing (a later acceptance replaced the control, say) records nothing.
- **History.** Each version is adopted from the moment it is assembled, never backdated to the instant, so no recorded evaluation is ever outside the adoption it names. Between the instant and the worker's pass (normally seconds) the earlier version stays the rule.
- **What a person sees.** The controls list also shows an accepted control outside its interval: `period: upcoming` ("Takes effect on …") before it starts and `period: ended` ("Ended on …") after, each with one `not_applicable` result and no evaluation. A listed-subject rule outside its interval is shown only where its subjects are in scope, as when it is in force.
- **Controls accepted before 0069.** They had no boundary queued. Migration 0072 queues, once, the rows the worker would have queued when it projected each organization's latest decision that can change the set: one per later instant at which a bound control's interval starts or ends, triggered by that decision. It rewrites nothing. The unique index of 0069 keeps an instant already queued as it is, so running it again, or after boundaries were queued, adds nothing; an instant already past is due at once and the worker reassembles from now. No application or worker step runs once at start or sweeps on a schedule, so a migration is the one place that runs exactly once with several workers.

## 5. Verifiable offline

The adoption event carries the whole pack, as every adoption does. The pack digest, each leaf digest and each source hash recompute from it; finding packets and `tools/verifier` already check an evaluation against the adoption it names this way, with no registry. With the SMS export, a reader can rebuild each leaf from the control version its reference names (body digest) and the registered type's declaration.

## 6. Migration 0067

A unique index on (tenant, organization, pack version) for adoptions of `ledger.accepted-controls`, so two processes cannot record the same version even if the organization lock were bypassed. With `organization_pack_adoption_revised_once` (0052) the versions form one chain. No table is added: the adoption row is the pack's home.

## 7. What a person sees

`GET /v1/flights/{id}/controls` lists the controls in scope for a flight. The subjects in scope are those release policy version 2 reads findings about: the flight, its organization and the subjects its current records name.

- A control with rules is in scope for each in-scope subject of a rule's target kind (for listed subjects, only listed ones). Its result per subject is the latest evaluation under the current leaf digest: pass, attention, insufficient (pending, conflicting, or not yet evaluated under this version) or not applicable. With no such subject in scope, it is shown once as insufficient, unless it lists its subjects.
- An area control reaches the same list: its result is route review's for the flight's mission (outside: pass; intersects: attention; otherwise insufficient).
- Any other control in force is listed as needing a person's confirmation.

Release, briefing and departure show this list with each control's wording, as they show avoidance: the mission review screen (route review, release form and departure progress) and the briefing screen. The avoidance demonstration's guided mission screen leaves it out, as it leaves out departure progress; its guided briefing screen shows it, since a briefing pins it. No recorded scene opens these screens. Results from the rules are ordinary findings of an active adoption, so they also appear in the release basis that policy version 2 pins. Nothing is blocked or allowed automatically.

## 7a. Briefing and departure pin the list

A briefing and a departure authorization pin the controls in scope the person saw, as release policy version 2 pins findings.

- **The list.** `GET /v1/flights/{id}/controls` returns `digest`: canonicalDigest of `{version: 'flight.controls-seen.1', controls, complete}`, without the instant it was read. Each listed control carries its version, body digest, wording, period and results, each result with its rule digest and evaluation digest where there is one.
- **The command.** `mission.brief` and `mission.departure-authorize` take `expectedControlsDigest`. When sent, the list is read again in the command's transaction; a different digest conflicts (`409 flight_controls_changed`, with the current digest) and records nothing.
- **Required while controls are in scope.** A command without the digest reads the list in its transaction. If the list is not empty it is refused (`409 flight_controls_not_seen`: the record would not say which controls the person saw) and records nothing. With an empty list it records version 1 as before. The commit triggers are unchanged: they check that a named digest equals the pinned section's, but cannot rebuild the list, which needs each control type's registered declaration, so the requirement is the application's, in the same transaction and under the same locks as the pin.
- **New versions.** A briefing that pins the list is record version `flight.mission-briefing.2`: version 1's fields plus `controls`, the list with its digest. A departure authorization keeps its permit (`flight.mission-departure-permit.1`, what a consumer holds) and pins the list in issuance basis version `mission.departure-issuance.2`. A command without the digest, allowed only while no control is in scope, records version 1 exactly as before; every existing record stays valid and verifiable unchanged.
- **Database.** Migration 0069 widens each table's record identity check to either version, the later one with its section, and redefines the briefing and departure commit triggers with one change: the command may name the digest, and then it must equal the pinned section's.
- **Screens.** The briefing screen sends the digest of the list it shows, including on the avoidance demonstration's guided briefing, which now shows the list too; it offers "Record briefing" only once the list has been read. A recorded version 2 briefing says how many controls were pinned with it. The departure authorization is issued by the operation's own flow, not a screen.
- **The simulator.** The simulated departure reads the list during its review and sends its digest. On `flight_controls_changed` it reads the list again and sends a new command under a new key, up to three reads in all; then the refusal stands and the flight is recorded as not departing (abandoned with that code), an ordinary outcome of the simulated day.
- **Offline.** `tools/verifier` checks a pinned list's shape, that its digest reproduces and that it equals the digest the command named, and states that it cannot show the list was complete, that each control was in force or each result current when recorded, or that a listed evaluation is in the inventory.
- **Size.** A briefing record stays within its 128 KiB budget; a list too large to pin is refused with the existing budget error.

## 7b. One briefing covers several controls

Every accepted area control whose interval overlaps a flight's is a candidate of its route review, wherever it is, and each needed its own briefing and acknowledgement round. Which controls are candidates is unchanged; one briefing may now cover several of them, so a flight needs one round however many there are.

- **The command.** `mission.brief` takes `controls`: one to 64 (the route review's candidate bound) exact candidate references, each the reference `control` carried (hazard, control, version, version event, body digest, acceptance), each once and in the order the release lists its candidates. A repeated control or another order is refused (`400 briefing_controls_invalid`); a reference that is not an exact candidate of the release, including a stale version or a control not overlapping the flight, conflicts (`409 briefing_control_mismatch`) as the single one did. A command that names `control` is refused (`400 briefing_controls_required`): the web app and the tests were its only senders and all list now.
- **The record.** A new briefing is record version `flight.mission-briefing.3`: `context.controls` holds the references and `content.controls` the briefed content of each at the same position. Top-level `controls` stays the controls-in-scope list of 7a, pinned whenever the command names its digest. Versions 1 and 2 keep their rows and checks; each reads as a list of one control.
- **Acknowledgement.** One acknowledgement acknowledges the briefing, hence every control it lists. A briefing past its `valid_until` (the release window's end, or an earlier start or end of a control that can matter to the flight) has lapsed and cannot be acknowledged (`409 briefing_lapsed`); see control-applicability.md section 7. The briefing screen shows each listed control (its title, the wording its type gives it, its area and the route's relation to it as the release recorded it) above the review checkbox.
- **Departure readiness.** Every release candidate must be named with an exact, current, acknowledged briefing that lists it. One briefing may be named for several candidates, and a candidate may be covered by any briefing that lists it, of any version. A briefing covers exactly the controls it lists, and only while it is in force: a lapsed briefing does not count even when it was acknowledged in time.
- **Database.** Migration 0074 adds version 3 to the record identity check and redefines the briefing commit trigger: it checks each listed control as it checked the one (an exact candidate whose retained version matches the briefed content), refuses a list that repeats a control or leaves the release's order, and requires the command to name the same list. Its locks and their order are unchanged. The departure trigger reads no briefing and is unchanged.
- **Screens.** Departure progress lists each control with the briefing that covers it and offers one "Prepare the controls briefing" for all controls that still have none. The briefing form starts with those controls selected (every control of the release when nothing was requested) and the author may narrow the selection.

## 7c. One version of each mission record

Ledger has no users yet, so the superseded versions that 7a and 7b kept beside the current ones are deleted. A briefing is only `flight.mission-briefing.3` (it may still leave out the pinned list when no control was in scope), a release only `flight.mission-release.2` under release policy version 2, and a departure authorization's issuance basis only `mission.departure-issuance.2`. A departure command may still leave out the digest while no control is in scope; its basis then pins the empty list, so every authorization records the list its authorizer saw. Migration 0075 narrows each record identity check to the current version, redefines the briefing commit trigger without the single-control branch and the departure commit trigger to accept a missing digest only for the empty list, keeping their locks and order. It deletes nothing: it refuses a database that holds a row of a deleted version and says to recreate it.

## 8. Limits and follow-ups

- A new rule is not run over observations recorded before it was adopted.
