# Check kinds for record-keeping rules

Status: built. Added since: read narrowing, anchored reads, subject state and wording; kinds over more than one record (code: `packages/domain/src/check-kind-library-combined.ts`, tests: `packages/domain/tests/check-kinds-combined.test.ts`); kinds over positions and areas; kinds over every value in a window, and reads within a window. Code: `packages/domain/src/check-kind-library-records.ts`. Tests: `packages/domain/tests/check-kinds-records.test.ts`. Builds on the first library (`check-kind-library.ts`) and the operator record types (`operator-records.md`).

These kinds let a rule pack ask the questions record-keeping rules ask: is a record held and complete, is a date recent enough, does a recorded interval cover a window, do duty and rest periods stay within limits, is a recorded quantity within a limit, does a record hold an expected value, and is an occurrence recorded. None names a regulation, record type or threshold: the rule gives the record type, fields and limits as parameters.

## Common to every kind here

- **Replaced and withdrawn records never reach a kind.** The observation reads leave them out, at the evidence cut the evaluation reads at (`observation-corrections.md`). No kind looks for replacements.
- **`select: 'latest'` no longer returns a replaced record.** A replaced record is not read, so the latest read is the current one. `latest` still reads only the newest observations of the type, and every operator record type arrives as `operator.record`; a kind that selects one record type from it needs `select: 'all'`, or the newest record of another type can hide it. Mark record reads `required: false`: every operator record type arrives under one observation type, so the engine's required-input test is met by a record of any type. The kind reports a missing record itself.
- **Narrow the read by record type (preferred).** Every operator record type arrives under one observation type, `operator.record`. Give the rule's read a `where`, such as `[{ field: 'values.recordType', oneOf: ['<record type>'] }]` (add `values.recordVersion` the same way when the version matters). The engine applies it while gathering, so `required`, `select`, applicability and the 500-observation page limit see only matching records: a `required: true` read is then `insufficient` when only other record types exist. A read without `where` still counts a record of any type towards `required`; mark such reads `required: false` and let the kind report a missing record.
- **Selection inside a kind.** Where a kind takes a `select` (or `dutySelect`, `windowSelect`, …) parameter, it is `{ recordType?, recordVersion?, where? }`. `recordType` and `recordVersion` (given together) keep only operator records of that type; `where` is a list of conditions, each `{ field, oneOf: [values] }` or `{ field, filled: true }` (absent, null and blank text are not filled; false is). Fields are dot paths into the observation, so a record body field is `values.record.<name>`, and a reference field is compared by its id, `values.record.<name>.id`. A pack file's paths are checked against the record types when it is built and loaded ([pack-files.md](pack-files.md#loading-and-verifying)); [write-a-rule-pack.md](../guides/write-a-rule-pack.md#a-rule-by-check-kind-start-to-finish) works one rule through from a manual's sentence.
- **Results.** A missing record, value, limit or window is `insufficient`, never a pass. Simultaneous observations that disagree are `conflicting`. Times are UTC throughout; calendar months are counted on UTC calendar dates.
- **Earlier versions stay.** `record.complete@1`, `value.within-limit@1`, `date.within-months@1` and `interval.covers-window@1` are unchanged and still suit non-record observations of a single type. The version-2 kinds add selection; prefer them for operator records.

## Evaluated as of each flight

A rule about a flight asks its question as of that flight, never as of the day it is evaluated. Every evaluation still records the time it ran, but a kind that reads records about the flight's aircraft, pilots or organization places them against the flight's own time. Kinds written after this rule follow it; `due.time-or-total@1` was the first.

- **The flight's time.** The takeoff a source reported, else the takeoff in the operator's own flight record, else the start of the planned window; and for a window, the landing, else the planned end, from the same record. Each is read only when the rule names its field, and the sentence says which it read ("at takeoff", "at the planned start"). A planned start still to come is read with what is on file so far.
- **A record in effect.** The latest matching record made at or before the takeoff. A record made after the takeoff is never read for it, so a check recorded the next day does not cover yesterday's flight.
- **A count or an age.** A count is taken over the window that ends at the takeoff (the 90 days before it, not the 90 days before today); an age is the time from the record to the takeoff.
- **Overlaps.** The intervals that overlap the flight's window: flown where on record, else planned.
- **Nothing on file.** Where the operator's records cannot show the answer (no takeoff or plan, no record at or before the takeoff), the result is `insufficient`, reason `record_not_on_file`, and the sentence names what is missing. It is never `supported`.
- **The sentence.** States the values it read in the operator's own ids (the aircraft, the pilot, the other flights) and the times it compared; the engine writes each instant in the organization's time zone.

The earlier time's own day is not counted; the time runs out at the local midnight after the Nth business day. - **The time zone is a parameter, never guessed.** It is validated twice: by pattern (an `Area/Location` name or `UTC`; abbreviations such as `MST` and offsets such as `-07:00` are refused) and by the platform's `Intl` time-zone data when evaluated (`time_zone_unknown`, `insufficient`). The machine's own zone is never read. A rule may leave `timeZone` to an adoption parameter (it is a string scalar). With `timeZoneField`, an observation that records a different zone conflicts rather than being counted in the wrong calendar. Results depend on the time-zone data of the Node.js build that runs them.
- **The intersection of two windows is a kind of its own**, not a parameter shape on `interval.covers-window`. Version 2 of that kind is pinned in shipped packs and cannot gain an input, so it would have needed a version 3 anyway; and a version 3 with a second window would carry modes that no longer fit together (cover the evaluation instant, one window, or two). As its own kind both windows are required inputs, a missing one is `insufficient`, and what happens when they share no time is a stated parameter.
- **Excluded dates belong to the rule.** Adoption parameters are scalars, so the list of excluded dates and its covered range are fixed in the rule; a new year of excluded dates is a new pack version.
- **Two records about different subjects** (an aircraft's make and model against a person's experience, a component's life limit against its aircraft's time) need the related reads of [fan-out-and-related-reads.md](fan-out-and-related-reads.md) to reach the check. The kinds here compare whatever two inputs the rule reads; they do not resolve references.

## Kinds over positions and areas

Code: `packages/domain/src/check-kind-library-geometry.ts`. Tests: `packages/domain/tests/check-kinds-geometry.test.ts`.

| Id and version | Inputs | Parameters | The question it answers | Details |
| --- | --- | --- | --- | --- |
| `position.in-area@1` | `positions`; `area` (optional) | `select?`, `expect` (`inside` or `outside`), exactly one area: `area` (a circle `{ center: { latitude, longitude }, radiusMeters }` or a GeoJSON `Polygon`, fixed in the rule), `centerLatitude` with `centerLongitude` and `radiusMeters` (scalars, so an organization can set a circle on adoption), or `areaField` with `areaSelect?` (the circle or polygon in a field of the latest selected `area` observation); `marginMeters?` (grows the area; negative shrinks it); `maxHeightMeters?` with `heightDatum` (only with `expect: inside`); `minPositions?`, `minSeconds?`; `unusable?` (`[{ field, oneOf }]`); `accuracyField?` with `maxAccuracyMeters`; `scope` (`latest` or `any`) | Does each position (the observation's own `position`) keep inside an area, or out of one? Consecutive positions on the wrong side make an excursion, which counts once it has `minPositions` positions and lasts `minSeconds` from its first to its last position; one not yet long enough is `insufficient` / `pending` (`excursion_unconfirmed`). With `latest` only the excursion going on at the newest usable position is checked, so the result passes again once the subject is back; with `any` every excursion among the positions read counts. Positions outside the coordinate profile, matching an `unusable` condition, or stating an accuracy worse than the limit are left out and listed in the summary; an unusable fix neither ends nor extends an excursion. No area, an invalid area, or no usable position is `insufficient`; simultaneous area observations that disagree conflict. | `areaShape`, `marginMeters`, `positionsChecked`, `unusablePositions`, `heightsUnchecked`, `latestDistanceOutsideMeters`, `excursionStartedAt`, `excursionLastAt`, `excursionSeconds`, `excursionPositions`, `maxDistanceOutsideMeters`, `maxHeightAboveLimitMeters` |

- **Geometry.** The area is closed: a position within a millimetre of the boundary is on it, so it is inside a keep-in area and inside a keep-out area. Distances are geodesic on the WGS84 ellipsoid with the route review kernel's library (`geographiclib-geodesic`), coordinate profile (latitudes within 80 degrees, no edge across the antimeridian), numerical margin, largest circle radius (10 km) and largest polygon perimeter (50 km, at most 256 positions per ring, 20 rings). The kernel itself only answers whether a route meets a circle, so the kind measures a position with the same geodesic rather than calling it. Polygon edges are straight in a plane centred on the position (azimuthal equidistant), so the distance to a corner is exact and the distance to an edge is close to it at the size of an operating area. Holes are honoured (even-odd).
- **The area shapes.** The circle is the shape of the avoidance-area control type and of accepted area controls (`controlArea`); the polygon is GeoJSON, as the Airspace Link emulator's operation boundary is. The operating area record (`organization.operating-area`) states a circle or a corridor as a person types it, and version 2 reads it with `areaRecords` (below).
- **Areas from records (version 2, `areaRecords`).** `{ idField, shapeField, centerField, radiusField, pointsField, halfWidthField }` name where each record of the `area` input states its id, its shape (`circle` or `corridor`), a circle's centre (`latitude, longitude` in decimal degrees) and radius, and a corridor's points along its line (pairs separated by semicolons, 2 to 200) and half-width. Every selected record is an area while its interval holds the position's time (no end: from its start on), and a position inside any area then in force is inside; a position with none in force is outside, at no stated distance, and the summary says so. A radius or half-width above `OPERATING_AREA_SIZE_LIMIT_METERS` (50,000 m, in `packages/contracts/src/operating-areas.ts`, the record field's own maximum) or a record whose area cannot be read is named in the summary and left out; with none left, the result is `insufficient` (`area_invalid`); with no record, `area_missing`. A corridor is every place within its half-width of the geodesic line through its points: each leg is halved along its geodesic until a piece is at most 1 km, measured in a plane centred on the position, and a piece that cannot come nearer than the nearest distance already found (by the triangle inequality) is not halved further, so a long leg is measured as closely as a short one. Areas are named in the order of their ids, so a summary never depends on Ledger's own.
- **Quality.** `position.fix@1` says a fix of `none` or `unknown` is not a reliable location, but which values a rule treats as unusable is the rule's choice, given in `unusable`. A source that reports no fix quality at all (every fix `unknown`) leaves a rule the choice between using its positions, saying so, and having no usable position.
- **Height.** Compared only where the position states an altitude in `heightDatum` (`position.fix@1`: altitude may be compared with a limit only when the datums match). Other positions are counted in `heightsUnchecked` and still placed horizontally.

## Kinds over every value in a window

The earlier kinds look at the latest value, so "within the limit for the whole flight" could not be asked, and they named no issues, so an indicator could count findings but not exceedances.

| Id and version | Inputs | Parameters | The question it answers | Details |
| --- | --- | --- | --- | --- |
| `window.values-within-limit@1` | `values`; `window`; `limit` (optional); `recorded` (optional) | `select?`, `field`, `comparison` (as `value.within-limit@2`), either `limit` or `limitField` with `limitSelect?`; `windowSelect?`, `windowStartField?`, `windowEndField?` (default the window observation's interval); `includeValueAtStart?`; `minValues?`, `minSeconds?` (the tolerance); `maxGapSeconds?`; `coverage` (`required` or `optional`); `recordedSelect?`, `recordedField` with `recordedAtField`, `recordedDescribes`, `reportedDescribes`, and `recordedStartField` with `recordedEndField` (the operator's own record, read when nothing is reported: [observed-values.md](observed-values.md), section 7) | Is every value whose span start falls in the window within the limit? | `position.in-area@2` | `positions`; `area` (optional); `window` (optional) | As version 1, plus `windowSelect?`, `windowStartField?`, `windowEndField?`, `coverage?` (`required` default, or `optional`), `areaRecords?` (below) and `areas?` (several areas fixed in the rule, each `{ id, center, radiusMeters }` or `{ id, points, halfWidthMeters }`: inside any one is inside) | As version 1, over the positions in the window when the rule reads one. **Each counted excursion is one issue**, named `excursion-from:<start>` and timed from its first position to the first position back on the right side (or its last position once the window has closed). Version 1 is unchanged. | Version 1's, and `windowStart`, `windowEnd`, `windowClosed`, `excursionCount`, `secondsOutside` |

- **The window.** The latest selected `window` observation states it by its start and end fields: a flight report (`values.takeoffAt` to `values.landingAt`), or the subject state named `window` (`scheduledStart` to `scheduledEnd`). Both ends belong to it. No valid start, or an end before the start, is `insufficient` (`window_missing`); simultaneous observations stating different windows conflict.
- **An open window.** Without a stated end, or before it, the window is open: the result covers what has been reported so far, says so in its summary and in `windowClosed: false`, and a run still going on that is not yet long enough to count is `pending` (`outside_unconfirmed`). A run going on counts as an issue with no end, and keeps its name when the window closes, so an indicator counts it once.
- **The same answer during and after.** Nothing outside the window is read and nothing depends on the evaluation time except whether the window is still open, so a result evaluated after the window closes does not change when later values arrive. Read the values with the `within` selection below so that the engine also leaves them out.
- **Coverage.** Observations in the window without a numeric value are `missingValues`; with `maxGapSeconds`, longer stretches without a value (from the start, between values and to a closed window's end) are gaps. With `coverage: required` either makes an otherwise passing result `insufficient` (`coverage_gap`), and a closed window with no value is `insufficient` (`values_missing`); with `optional` a closed window with no value does not apply (`no_values_in_window`). An open window with no value yet is `pending` (`values_awaited`).
- **A rule names the window read `window`**, because that is the kind's input name; it can still be the relation's `from` read and carry the applicability conditions.

### Reading every observation in a window

A read's `select` gains `{ within: { read, startField, endField } }`: every observation (up to the page limit of 500, newest first) whose span start lies from the instant in `startField` to the instant in `endField` of the latest observations of an earlier read or the subject-state read; without an end, up to the evaluation time. Without one valid start, or with an end before the start, the read is empty. The engine reads from the window start (`listObservations` `from`) rather than from the earliest time, so observations about the related subject after the window, such as wind the site reports long after a flight, never enter the read, its input digest or its page limit. A window holding more than 500 matching observations is `input_limit_exceeded`, as any read. Other selections read exactly as before.

## Which to use: a read's `where` or a kind's selection

- Use a `where` on the read when one input holds one kind of record, which is the usual case. It keeps other record types out of `required`, applicability and the page limit, and the evaluation lists only the records the rule read.
- Use the kind's own selection only when one input must hold several record types that the kind tells apart, such as duty and rest periods read as one `periods` input (`dutySelect`, `restSelect`), or a window record read beside the records it bounds.
- The two combine: a read narrowed by `where` can still be split by the kind's selection. The record kinds above keep their selection parameters unchanged; a rule written before `where` existed behaves as it did.

## Other read features

- **The latest observation at or before another read's instant.** `select: { latestAtOrBefore: { read, field } }` takes the observations sharing the newest span start at or before the instant in `field` of the latest observation of `read`, an earlier read or the subject-state read. Without exactly one valid UTC instant there the read is empty, so a required read is `insufficient`. Example: the battery reading at or before the recorded landing time.
- **The subject's own state.** `subjectState: { name, required }` on the leaf reads what Ledger holds about the evaluated subject, through the loader the module that owns the subject kind registers (`registerSubjectState`). A flight exposes `status`, `scheduledStart` and `scheduledEnd`. The state reaches the check as one observation under `name` (fields at the top level, so `deadlineField: 'scheduledEnd'` for `evidence.due@1`), its revision is part of the input digest, and a change of state queues the rules that read it. Each evaluation records the state content it read with its revision (the digest of that content), and a state change is queued and recorded with trigger kind `state` and the event that made it. The flight projection keeps only the current state, so a replay at an earlier evidence cut cannot read the flight's old state from the projection: the content recorded on the evaluation is the authority for what that evaluation read.
- **A date alone.** A record placed by a date alone, or a report or notice time given as one, keeps the day in `values.dayOnly`; `record.made-before@1`, `events.answered-within@1`, `business-days.within@1` and `due.time-or-total@1` read the instant of that day least favourable to the operator and say only the date is on record, and `record.before-flight@1` counts a check dated a day for the flights of that day or the flight it names ([date-only-records.md](date-only-records.md)).
- **A rule that applies without a report.** An applicability condition with `whenAbsent: applies` is met when no observation of its input is on record, for a rule that reads either a source's report or the operator's own record.
- **Wording.** `wording: { pass?, attention?, pending?, not_applicable? }` replaces the check's own summary for a result the check returns. `{name}` placeholders are filled only from the details the check kind declares and returns; a pack whose template names an undeclared detail, or states a verdict, is refused when registered. If a named detail is not returned, the check's own summary is used. `values.disagree@1` returns `values`, `valueCount` and `reportCount`; `evidence.due@1` returns `dueAt`, `graceSeconds`, `evidenceFound` and `evidenceValues`. The kinds over more than one record return the details listed in their table (a detail that is null leaves the check's own summary in place); the other record kinds return none yet.
- **Labels, not paths.** A summary a person reads names a record by its record type's title and a field by its label: "No value is recorded for the flight plan’s Operating authority", "The latest training record is missing: Training materials reference, Provider name". The words come from the registry at the source, in the kinds (`field-labels.ts`): an operator record's field resolves to its record type's title and the field's label; a field of another observation to its observation type's title and the title its schema gives the field; the value of a field with options to the option's label. With no such observation to read from, a field falls back to a readable form of its name ("the operating authority reference"), never the path. A path, a record type id and a raw value stay in the machine-readable parts of the evaluation (its parameters, inputs and details). Summaries are not part of a kind's definition, so no check kind, pack or evaluation digest moved; the golden summary digest in `tests/unit/check-summary-wording.test.ts` did. `tests/unit/summary-labels.test.ts` evaluates every shipped rule on no input and on records that are there but empty, and fails if a summary holds `values.`, a record type id with `@`, or a camel-case name.
- **Units and times as the organization reads them.** A sentence states a quantity in the unit its rule's text uses, when the rule declares it in `textUnit` (`m`, `km`, `ft`, `mi`, `nm`, `m/s`, `km/h`, `kn`, `mph`), with the stored value beside it in parentheses: "400 ft (121.92 m)" (`quantities.ts`). `value.flown-or-planned@1`, `authorization.covers-flight@1` and `position.in-area@2` take it; the Part 107 rules (heights and authorizations in `ft`, ground speed in `kn`) and the waiver library's `condition.max-height` (`ft`) and `condition.max-distance` (`mi`) declare it. Without it a quantity is stated in its stored unit, as before. Every instant a recorded summary states, the kind's own or a rule's wording filled from the details, is written in the organization's time zone with the zone's name ("2026-11-10 09:05 America/Denver"); the evaluation records the zone in its `clock.timeZone` and in its observation digest, so a changed zone evaluates the rule again. Details keep their UTC instants. The kinds' digests moved for `textUnit`, and with them the digests of the packs that use them.
- **A check's own summary as wording.** A kind may name, in `summaryValues`, the details whose values its own summaries state word for word (today the UTC instants: `evidence.due@1` `dueAt`; `total.from-opening@1` `openingAt`; `interval.covers-intersection@1` `windowStart`, `windowEnd`, `uncoveredFrom`; `position.in-area@1` `excursionStartedAt`, `excursionLastAt`, and `@2` also `windowStart`, `windowEnd`; `window.values-within-limit@1` `windowStart`, `windowEnd`, `worstValueAt`). Nothing new is recorded: a read derives the wording from the recorded summary by putting a `{name}` placeholder where each named value stands, and returns it in `summaryWording` beside the record, as it does a rule's wording. It is returned only when filling it with the recorded values, each instant written in the recorded zone, gives the recorded summary exactly, so a screen may write the times its own way and name the subjects. `summaryValues` is outside the kind's definition, so no check kind, pack or evaluation digest moves. A kind may also list, in `summaryRecordValues`, instants its summaries state that are fields of the evaluation record rather than details, from a closed set: `nextBoundary` (placeholder `{nextBoundary}`) and `evidenceOccurredAt` (the recorded time of each cited observation, `{evidence0OccurredAt}`, `{evidence1OccurredAt}`, …). `interval.covers-window` @1/@2 list `nextBoundary` ("in effect until"); `window.values-within-limit@1` lists `evidenceOccurredAt` (the start of a run not yet long enough). The values come from the record through `summaryRecordValues` in contracts, on the server and on screens alike. A value a summary states that the record does not hold (an observation id; the limit end of `value.within-limit@2`; the later time of `business-days.within@1`) stays as recorded.

## Parameters an organization sets

Adoption parameters are scalars merged at the top level, so an organization can set `months`, the hour limits of `duty.within-limits`, and a fixed `limit`. Selections are fixed by the rule.

## Not covered here

These need engine capabilities that do not exist yet. A rule should not work around them.

- One result per person in a role or per installed component (fan-out).
- Reading a related subject's records: the aircraft a component is installed on, the person a flight's assignment names.
- Comparing fields of two different records (a person's experience make and model against the aircraft's). **Closed by `field.matches@1`** for two inputs the rule can read; reading the aircraft a flight's person will operate still needs the related reads.
- Deriving a total from many observations (aircraft time from an opening balance and later flights). **Closed by `total.from-opening@1`.**
- Calendar days in a local time zone. Operator-recorded day and week totals can be checked with `value.within-limit@2`. **Closed by `local-days.total@1` and `business-days.within@1`.**
