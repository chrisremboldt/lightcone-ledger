# Metrics and the request limit

What a deployment can measure and how its credentials are limited, and why they are built as they are.

## Metrics

**A listener of its own.** Each process serves `GET /metrics` on an address and port from `LEDGER_METRICS_LISTEN`, loopback when only a port is given, and never on the port of the API and the web app: a proxy that publishes the API cannot publish the metrics by mistake, and the API refuses to start when the two ports are the same. Unset, nothing listens and nothing is measured. The one-process start makes one registry and passes it to the API and the workers, so the process has one endpoint; the image's supervisor, which runs them as two processes in one container, gives the workers `LEDGER_WORKER_METRICS_LISTEN` instead, since two processes cannot listen on one port.

**Written by hand.** `packages/metrics` is a counter, a gauge, a histogram, the text format and a `node:http` listener in a few hundred lines. `prom-client` was considered: it would bring default metrics and label handling we would have to restrict anyway, and a dependency for something this small.

**Nothing in a label names anyone.** Label names come from one list in `packages/metrics/src/registry.ts`; a metric declaring any other is refused when it is registered. Every value is checked too: a value that looks like an id (a UUID, a run of four or more digits) or holds characters a path's query or an address needs is refused. A request is counted under its route's template from Fastify (`/v1/flights/:id`), or `unmatched`, never its path. `tests/unit/request-metrics.test.ts` sends requests whose paths carry ids and fails if any of them, or a label outside the list, reaches the exposition. A new label name is added to the list with a test that says where its values come from.

**Queue depth from one counting function.** The workers connect as `ledger_worker` under row-level security, which shows a connection one organization's rows at a time, so no ordinary query can count every organization's waiting work. Migration 0092 adds `ledger_queue_figures()`, a security-definer function written like the lease functions beside it: one row per queue with the items ready to run now (pending and due, or leased with the lease run out), the items under a live lease, and the oldest ready item's age. It returns no id and no organization, and only `ledger_worker` may execute it. The workers' metrics call it at each scrape, so the depth costs nothing between scrapes; if the database cannot be read the gauges keep their last values and `ledger_queue_figures_timestamp_seconds` shows how old they are. The evaluation lag is the oldest ready age among the evaluation queues. Each worker process also reports what it leased itself (at most 20 an item a pass, with each item's wait), which shows how the work is shared out. Considered: counting per organization from the process, which needs the list of organizations the worker cannot read, and a counting role with `BYPASSRLS`, which would read every row rather than counts.

**Leases.** The six queue loops (the four of projections, rule selection and evaluation, and the two of notices) share one function (`runLeases` in `apps/workers/src/work-metrics.ts`) that runs each leased item, records a retry for one that failed, and tells an observer what became of it: completed, lost (the item's lease no longer matched, or ran out before commit) or failed. A lost connection stops the pass without counting against the work, as before. Notice attempts are counted by channel and outcome (sent, failed, given up), never by recipient or address. A queue added later adds its name to `WORK_QUEUES` and a branch to `ledger_queue_figures()` in a new migration.

## The request limit

**A token bucket per credential, per process.** Each API process keeps, in memory, a bucket for each credential that has sent a request: a burst it may send at once and a steady rate it refills at. The key is a SHA-256 digest of the bearer token, or of the issuer and subject for a person's sign-in token (which changes on each sign-in while the person does not). Full buckets are dropped when many are held, since a full bucket is the same as none. Two processes allow twice as much; a shared store (the database, or another service) would make the limit exact across processes at the cost of a write per request, which is not worth it for a limit meant only to stop a runaway client.

**Two pairs.** A source's credential, which an adapter uses to deliver observations, gets a higher pair (200 a second, 2,000 at once) than a person's, a service's or an agent's (20 and 300). Both are meant never to be met in ordinary use.

**Where it is off.** With `LEDGER_ENV=local` or `test` it is off unless `LEDGER_REQUEST_LIMIT=on`, so the simulated day, the demonstration recorder, the browser tests and the integration suite, which send many requests with one credential, are never throttled; the limit's own tests turn it on. Everywhere else it is on unless `LEDGER_REQUEST_LIMIT=off`.

**What it answers.** 429 with `Retry-After` and the API's usual error shape (`request_limit`, with `retryAfterSeconds` in its details), counted in `ledger_http_requests_limited_total` by the kind of credential. The adapter process already treats 429 as a reason to send the payload again. Requests without a credential (sign-in, the report page a reporting link opens and its routes, a link to a produced set of records, the web app's files) are checked before any credential is read, so they stay the proxy's to limit.
